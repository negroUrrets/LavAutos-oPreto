2. Problema y alcance

2.1 Problema

Un lavadero de vehículos necesita registrar a sus clientes, los vehículos de cada cliente y los lavados realizados, y conocer en todo momento en qué estado está cada lavado. Sin un sistema, esa información se dispersa en planillas o papeles, se pierden los vínculos entre cliente, vehículo y lavado, y no hay control sobre qué vehículos están en proceso ni sobre la evolución de los trabajos.

2.2 Usuarios y objetivo

El usuario es el administrador o empleado del lavadero, que inicia sesión con una cuenta predeterminada. El objetivo es centralizar la gestión de clientes, vehículos y lavados, con validaciones, estados controlados y consultas de seguimiento.

2.3 Funcionalidades incluidas

  • Inicio y cierre de sesión con una cuenta administradora predeterminada.
  • Gestión de clientes: alta, búsqueda, consulta, edición y baja (física o lógica).
  • Gestión de vehículos: alta, búsqueda, consulta, edición y baja, con catálogos en cascada.
  • Gestión de lavados: registro, listado por estado, avance de estado, edición y detalle.
  • Dashboard de consultas: lavados entregados por rango de fechas y clientes que no vuelven desde una fecha.
  • Bloqueo de edición y baja de clientes o vehículos con lavados activos.
  • Script de base de datos con esquema y datos iniciales, y seed de catálogos al iniciar.

2.4 Fuera de alcance

  • Gestión de usuarios y auditoría funcional de operaciones.
  • Stock y pagos: el README los menciona como idea, pero no están implementados; se declaran fuera de alcance.
  • Paginación de listados, exportaciones y reportes gráficos.
  • Despliegue en Internet y aplicación móvil.

4.2 Reglas de negocio

  1. El cliente de un lavado se obtiene por `Lavado → Vehículo → Cliente`; no existe una FK directa de lavado a cliente.
  2. Un vehículo no puede tener más de un lavado en estado activo (`En Espera`, `Lavando` o `Terminado`); el botón `LAVAR` se bloquea en ese caso.
  3. Estados del lavado: `En Espera → Lavando → Terminado → Entregado`. Los entregados no se muestran en el listado.
  4. No se puede editar ni dar de baja un cliente o vehículo con un lavado activo: el backend responde 409.
  5. Si hay lavados (no activos), la baja es lógica y los lavados se conservan; sin lavados, la baja es física.
  6. Eliminar un lavado no está permitido: el backend responde 405.
  7. Las utilerías se actualizan en el catálogo y el lavado guarda la primera utilería tildada.
  8. Las fechas del lavado las genera el backend; al cambiar el estado se actualiza `fechaHoraLavadoTerminado`.
  9. Dashboard: los lavados se filtran por `fechaHoraLavadoTerminado`; los clientes que no vuelven, por `fechaHoraLavado`.

El navegador ejecuta una SPA de React que consume la API REST con `fetch` y cookie de sesión. La API expone rutas bajo `/api`, protege los recursos con el middleware de sesión, delega la lógica en servicios y accede a SQL Server mediante modelos Sequelize. La base concentra el esquema, las claves y los datos iniciales.

6.3 Requisitos previos

  • Node.js 24.19 y npm 12 (probado con esas versiones).
  • Microsoft SQL Server accesible en `localhost,1433` (o la instancia configurada).
  • Permisos para crear la base `DataBaseLavadero` o una base ya creada.
  • Navegador actualizado; no se requiere conexión a Internet para ejecutar en local.

6.4 Instalación y ejecución

  1. Crear la base y el esquema: abrir `src/databaseLavadero/script db/DataBaseLavadero.sql` en SQL Server Management Studio (o `sqlcmd -S localhost,1433 -E -C -f 65001 -i "ruta\DataBaseLavadero.sql"`) y ejecutarlo. Crea la base, las tablas, claves, relaciones y los datos iniciales de forma idempotente.
  2. Configurar el backend: copiar `src/backend/.env.example` a `src/backend/.env` y completar `DB_SERVER`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_AUTH_TYPE`, `DB_DOMAIN` y `SESSION_SECRET` con valores locales ficticios. No versionar `.env`.
  3. Instalar dependencias del backend: `cd src/backend` y `npm install`.
  4. Opcional: cargar catálogos con `npm run seed` (el backend también los garantiza al iniciar).
  5. Iniciar el backend: `npm start` (o `npm run dev`). Inicio correcto: el mensaje `Backend escuchando en el puerto 3000`.
  6. Instalar dependencias del frontend: `cd src/frontend` y `npm install`.
  7. Iniciar el frontend: `npm run dev`. Inicio correcto: Vite informa `Local: http://localhost:5173/`.
  8. Abrir `http://localhost:5173` en el navegador. La aplicación debe mostrar el login.

El frontend usa un proxy de Vite hacia `http://localhost:3000` para `/api`.
